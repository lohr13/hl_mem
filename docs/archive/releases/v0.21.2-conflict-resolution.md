# v0.21.2 — Conflict Resolution Convergence

发布日期：2026-08-04

## 概要

v0.21.2 聚焦冲突案例从“已发现”到“终态一致”的闭环。自动维护不再只看初始 `pending` 状态，而是持续回访所有未决 case，沿 supersede 链识别当前端点；人工 CLI 裁决也会同步收敛 Claim 胜败者。新的列表字段和健康指标让人工审核与积压监控无需旁路查询。

## 自动冲突收敛

- `auto_resolve_conflicts` 扫描 `pending`、`auto_resolved`、`manual_required` 且 `resolved_at IS NULL` 的全部 case，避免 case 一旦进入中间状态便永不回访。
- 每个 case 在独立事务中重新读取并校验状态，沿 `superseded_by_id` 追踪到当前非 superseded 端点；循环、断链或并发变化会安全延后，而不会部分提交。
- 两端指向同一 Claim 时直接将 case 收敛为终态；仅一端已进入 `expired`、`retracted`、`archived` 等终态时，可将无其他未决争议的存活端恢复为 active，并记录 `keep_left` 或 `keep_right`。
- 权威度仍按确定性规则裁决；同权威 case 保持 `manual_required`，等待显式审核。

## 人工裁决与审计信息

- `hl-mem conflicts resolve <case_id> keep_left|keep_right` 会激活 winner，并把 loser 更新为 `superseded`，写入 `superseded_by_id`、`recorded_to` 和 `valid_to`。
- `hl-mem conflicts list` 为左右两端分别返回 value 摘要、Claim status、source authority 和 `recorded_from`，审核者可以直接比较内容、生命周期与来源强度。
- `coexist` 与 `reject` 的既有命令语义保持不变；case 状态转换继续由生命周期守卫和事务边界保护。

## 运维可见性

- `/healthz` 响应新增整数 `conflict_open_count`，统计 `pending`、`auto_resolved`、`manual_required` 且尚无 `resolved_at` 的 case。
- 健康端点复用应用生命周期 SQLite 连接读取该计数，不调用外部 provider，也不查询历史 LLM span；监控系统可直接对冲突积压设置阈值。

## 升级与兼容性

- 包版本、项目元数据和 lockfile 统一升级到 `0.21.2`。
- 本版本没有新增或修改 SQL migration；最新 migration 仍为不可变的 `036_tokenized_fts_v2.sql`。
- REST 路由和 MCP 工具契约不变；`/healthz` 仅新增向后兼容字段 `conflict_open_count`。
- CLI 的 `conflicts list` 仅新增输出字段；脚本消费者应继续忽略未知字段以保持前向兼容。
